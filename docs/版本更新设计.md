# 版本检查与更新设计

本文说明 zrss 的应用内检查更新：它是怎么实现的、发布前要准备什么、日常发版怎么操作、出问题怎么排查。

相关文件：

| 文件 | 作用 |
| --- | --- |
| `mygo.json` | 更新源（GitHub 仓库）与更新签名公钥 |
| `internal/app/updates.go` | 注册 MyGo 更新插件，导出检查/开关函数 |
| `internal/app/menu.go` | 应用菜单「检查更新…」 |
| `internal/app/tray.go` | 托盘菜单「检查更新…」 |
| `internal/app/ui_settings.go` | 设置窗口「更新」分组 |
| `internal/app/app.go` | `Run()` 里在 `App.Run` 之前注册插件 |
| `.github/workflows/release.yml` | 打标签后构建、签名并上传更新包 |
| `CHANGELOG.md` | 每个版本的更新说明，进入更新窗口与 Release 页面 |
| `scripts/keygen.sh` | 生成签名密钥 |
| `scripts/build.sh` | 带签名的本地构建 |
| `scripts/release.sh` | 发版前检查、打标签、发布与验证更新源 |
| `scripts/common.sh` | 三个脚本共用的路径、配置解析与签名密钥读取 |

## 1. 目标、边界与前置条件

- **应用内检查**：菜单、托盘、设置里都能检查更新。
- **零服务器**：更新清单和安装包放在 GitHub Releases，不需要自建更新服务。
- **签名验证**：客户端内置公钥，只接受用对应私钥签名的更新。
- **不打断阅读**：后台检查；有更新时才显示窗口；下载完可以选择重启，也可以下次启动生效。
- **不做的事**：不收集遥测、不上传阅读数据、不做账号体系、不支持降级。

开始之前需要：

- Go 1.27 或更新版本；
- 公开仓库 `zwdart/zrss` 的推送权限；
- GitHub CLI（`gh`，可选）：用于设置 Secret、查看 CI 和发布 Release；没有它也可以在 GitHub 网页上完成；
- 第一次配置时执行 `scripts/keygen.sh`，并把私钥写入仓库 Secret `MYGO_UPDATER_PRIVATE_KEY`。

脚本是 POSIX `sh`，macOS、Linux 与 Windows 的 Git Bash / WSL 共用同一套。Windows 自带 PowerShell 不能直接执行 `.sh`，请用 Git for Windows 的 Git Bash（本机路径通常是 `C:\Program Files\Git\bin\bash.exe`）或 WSL。

## 2. 整体结构

```text
zrss 启动
  └── mygo.Use(native.New(updater.Options{Language: "zh-Hans"}))
        └── App.WhenReady 后 10 秒首次检查
              └── mygo.Updater.Check(ctx)
                    ├── 解析 updates.github 的最新 Release
                    ├── 下载 update-<goos>-<goarch>.json
                    ├── 比较 manifest.version 与当前版本
                    └── 有更新 → 原生更新窗口
                          ├── 立即安装
                          ├── 跳过此版本
                          └── 稍后提醒（或自动下载）
                                └── 下载 .tar.gz → SHA-256 + Ed25519 验签
                                      └── 替换应用目录
                                            └── 重启或下次启动生效
```

更新方式来自 MyGo 的 `plugins/updater`，zrss 用的是它的 `native` 版本：更新窗口用 MyGo 原生 UI 绘制，不需要 WebView，和 zrss 其他窗口一致。

## 3. 配置

### 3.1 `mygo.json`

```json
{
  "version": "0.1.0",
  "updates": {
    "publicKey": "GRjAIRowOqQCLVbHg+FY6vC6tNEObzF3cRi9wFaCDIY=",
    "github": "zwdart/zrss"
  }
}
```

- `publicKey`：`mygo keygen` 生成的公钥，直接写进构建产物。
- `github`：`owner/repo`，必须是**公开仓库**。
- `github` 与 `url` 只能二选一；两个都填或都不填，构建会失败。
- `version` 必须是递增的语义化版本。客户端只提示比当前版本新的版本。

### 3.2 签名密钥

第一次配置时执行：

```sh
sh scripts/keygen.sh
```

或直接：

```sh
go tool mygo keygen -o .update-keys
```

会得到：

- `.update-keys/mygo-update.pub`：公钥，填进 `mygo.json` 的 `updates.publicKey`。
- `.update-keys/mygo-update.key`：私钥，**不要提交**，`.update-keys/` 已在 `.gitignore` 中。

把私钥写入 GitHub Actions Secret：

```sh
cat .update-keys/mygo-update.key |
  gh secret set MYGO_UPDATER_PRIVATE_KEY --repo zwdart/zrss
```

没有 `gh` 时，在浏览器打开
`https://github.com/zwdart/zrss/settings/secrets/actions`，新建 Secret
`MYGO_UPDATER_PRIVATE_KEY`，内容为 `mygo-update.key` 的全文。

同时把私钥放进密码管理器。**私钥丢失后，已经安装的用户将永远收不到新版本**，只能让用户重新安装。

### 3.3 更新源地址

构建后客户端实际请求：

```text
https://github.com/zwdart/zrss/releases/latest/download/update-windows-amd64.json
https://github.com/zwdart/zrss/releases/latest/download/update-windows-arm64.json
https://github.com/zwdart/zrss/releases/latest/download/update-darwin-arm64.json
https://github.com/zwdart/zrss/releases/latest/download/update-darwin-amd64.json
https://github.com/zwdart/zrss/releases/latest/download/update-linux-amd64.json
https://github.com/zwdart/zrss/releases/latest/download/update-linux-arm64.json
```

所以 Release 必须发布并标记为 **latest**；草稿或普通 Release 都会让这些地址返回 404。

## 4. 用户可见行为

### 4.1 检查时机

- 启动后约 10 秒做第一次检查。
- 之后默认每 24 小时一次。
- 检查失败后最多 1 小时重试一次。
- 电脑从睡眠唤醒时重新排期。
- 设置里关闭「自动检查更新」后，只在用户主动点击时检查。

### 4.2 入口

| 位置 | 操作 |
| --- | --- |
| 应用菜单 →「检查更新…」 | 立即检查，窗口马上显示 |
| 托盘菜单 →「检查更新…」 | 同菜单，并先把应用置前 |
| 设置 →「更新」 | 自动检查开关、自动下载开关、当前版本、检查按钮 |

### 4.3 更新窗口

窗口会按顺序显示这些状态：

1. **正在检查**；
2. **已是最新**（仅用户主动检查时显示）；
3. **检查失败**，附错误原因；
4. **发现新版本**：版本号、Markdown 更新说明，以及「安装」「跳过此版本」「稍后提醒」；
5. **下载中**：进度条；
6. **安装中**；
7. **可以重启**：立即重启进入新版本，或下次启动生效。

自动检查时如果用户之前点过「跳过此版本」，不会再弹窗；主动检查仍会显示。

### 4.4 状态文件

更新插件在 MyGo 用户数据目录写 `updater.json`：

```json
{
  "automaticChecks": true,
  "automaticDownloads": false,
  "skippedVersion": "0.1.0",
  "lastCheck": "2026-11-01T10:00:00Z"
}
```

- Windows：`%AppData%\zrss\updater.json`
- macOS：`~/Library/Application Support/zrss/updater.json`
- Linux：`$XDG_CONFIG_HOME/zrss/updater.json`

删除这个文件会恢复默认开关，并忘记「跳过此版本」。

## 5. 安全设计

- **签名算法**：Ed25519。公钥编译进客户端，私钥只存在于本地和 GitHub Secret。
- **完整性**：下载完成后校验文件大小与 SHA-256，再验证签名；任何一步失败都拒绝安装。
- **传输**：只通过 HTTPS 访问 GitHub。
- **权限**：
  - Windows 安装器安装到 `%LOCALAPPDATA%\Programs\zrss`，当前用户可写，因此能自更新。
  - macOS 替换 `.app` bundle。
  - Linux 替换可执行文件所在目录；AppImage 与包管理器安装的版本不允许自更新。
- **最小数据**：检查更新只发出对 GitHub Release 的请求，不携带订阅、文章或设备标识。
- **失败即停止**：验签失败、大小不符、写入失败都会保留当前版本，不会出现「更新到一半」。

## 6. 本地开发与构建

### 6.1 开发模式不会自更新

`go run .`、`go tool mygo dev` 属于开发构建，没有注入更新地址和公钥。点「检查更新…」会提示当前构建不支持更新，这是正常现象。

要验证更新，必须使用打包后的可执行文件，并把它放在当前用户可写的目录。

### 6.2 带更新清单的构建

```sh
sh scripts/build.sh
```

等价于：

```sh
export MYGO_UPDATER_PRIVATE_KEY=$(tr -d '\015\012' < .update-keys/mygo-update.key)
go tool mygo build -platform windows/amd64
```

构建完成后检查：

```sh
ls build/windows-amd64
```

应包含：

```text
zrss.exe
zrss-setup-0.1.0-amd64.exe
zrss-0.1.0-windows-amd64.tar.gz      # 更新包
update-windows-amd64.json            # 更新清单
```

没有 `update-*.json` 或 `.tar.gz`，通常是没有设置 `MYGO_UPDATER_PRIVATE_KEY`，或 `mygo.json` 没有配置 `updates`。

### 6.3 构建其它平台

```sh
sh scripts/build.sh --platform "windows/amd64,windows/arm64"
sh scripts/build.sh --platform linux/amd64
sh scripts/build.sh --platform darwin/arm64
```

本地交叉编译只用于检查产物；正式发布由 GitHub Actions 在对应系统上完成。

## 7. 发版流程

### 7.1 准备版本

1. 修改 `mygo.json` 的 `version`，例如 `0.1.1`。
2. 在 `CHANGELOG.md` 顶部添加一节，标题必须完全一致：

   ```markdown
   ## 0.1.1

   - 修复……
   ```

3. 提交：

   ```sh
   git add -A
   git commit -m "0.1.1"
   git push github master
   ```

> `mygo build` 会把这一节放进更新清单；没有对应小节时，签名构建会失败。

### 7.2 本地验证

```sh
sh scripts/release.sh
```

它会依次执行：

1. 检查 `CHANGELOG.md` 是否有当前版本小节；
2. 检查工作区是否干净；
3. `gofmt -l .`、`go vet ./...`、`go test ./... -count=1`；
4. 带签名构建当前平台的更新包；
5. 确认生成了 `update-*.json`。

### 7.3 打标签

```sh
sh scripts/release.sh --tag
```

脚本会创建并推送 `v0.1.1`（默认远端名 `github`）。推送标签会触发 `.github/workflows/release.yml`：

1. 校验标签与 `mygo.json` 的 `version` 一致；
2. 从 `CHANGELOG.md` 抽取本版本说明；
3. 创建草稿 Release；
4. 在 macOS / Windows / Linux 上构建；
5. 用 `MYGO_UPDATER_PRIVATE_KEY` 签名更新包、生成 `update-<platform>.json`；
6. 通过 `mygo build -upload` 把安装包、更新包与清单上传到草稿 Release。

### 7.4 等待并发布

```sh
gh run list --workflow release.yml -L 1
gh run watch <run-id> --exit-status
```

没有 `gh` 时，在仓库的 **Actions** 页面等待 Release 工作流完成。

CI 全部通过后发布：

```sh
sh scripts/release.sh --publish
```

它等价于：

```sh
gh release edit v0.1.1 --repo zwdart/zrss --draft=false --latest
```

没有 `gh` 时，在仓库的 **Releases** 页面打开草稿，确认更新包和 `update-*.json` 都在，然后发布并勾选 **Set as the latest release**。

脚本发布后会逐个请求六个平台的更新清单，打印清单里的版本号，用来确认更新源已经可访问。

### 7.5 端到端验证

1. 安装上一个版本（例如 `0.1.0`）。
2. 打开应用，等待自动检查，或点「检查更新…」。
3. 应看到 `0.1.1` 的更新说明。
4. 点安装，观察下载进度。
5. 重启后，设置 →「更新」里的当前版本应变为 `0.1.1`。

## 8. 脚本参考

| 脚本 | 作用 | 常用参数 |
| --- | --- | --- |
| `scripts/keygen.sh` | 生成签名密钥并打印公钥 | `--out <目录>` |
| `scripts/build.sh` | 带签名的本地构建 | `--platform`、`--upload` |
| `scripts/release.sh` | 发版检查、打标签、发布、验证 | `--tag`、`--publish`、`--skip-tests`、`--allow-dirty`、`--remote` |

示例：

```sh
# 只做本地检查和构建
sh scripts/release.sh

# 跳过测试（不推荐）
sh scripts/release.sh --skip-tests

# 打标签并推送，触发 CI
sh scripts/release.sh --tag

# CI 完成后发布并验证更新源
sh scripts/release.sh --publish

# 远端名不是 github 时
sh scripts/release.sh --tag --remote origin
```

`build.sh --upload` 用于本地手动上传到已存在的草稿 Release，需要：

```sh
export GH_TOKEN=$(gh auth token)
sh scripts/build.sh --upload
```

日常发版不需要它，CI 会自动上传。

## 9. 故障排查

### 9.1 点「检查更新」提示当前构建不支持更新

- 使用的是 `go run` / `go tool mygo dev`，属于开发构建。
- 或者 `mygo.json` 没有 `updates.publicKey` / `updates.github`。
- 或者应用所在目录当前用户不可写。

用 `sh scripts/build.sh` 构建后再试。

### 9.2 更新清单 404

```sh
curl -fsSL https://github.com/zwdart/zrss/releases/latest/download/update-windows-amd64.json
```

- Release 还是草稿：执行 `sh scripts/release.sh --publish`。
- Release 没有标记 latest：`gh release edit v0.1.1 --latest`。
- 文件名平台不匹配：检查 `build/<platform>/update-<platform>.json` 是否存在。
- 仓库是私有的：客户端无法匿名下载，改用 `updates.url` 或公开仓库。

### 9.3 有清单但客户端不提示更新

- 清单里的 `version` 不比当前版本新；客户端不会降级。
- 标签与 `mygo.json` 的版本不一致，CI 构建的是旧版本。
- 用户点过「跳过此版本」；手动检查仍应显示。
- 客户端是开发构建。

### 9.4 下载或安装失败

- 错误里出现 `signature` / `verify`：私钥与 `mygo.json` 的公钥不匹配。重新生成密钥对会改变公钥，旧用户将无法验证新更新。
- 错误里出现大小不符：上传的归档不完整，重新构建并上传。
- Windows 提示无法写入：应用被放在只读目录或由管理员安装到 `Program Files`；让用户安装到默认的 `%LOCALAPPDATA%\Programs\zrss`。
- Linux AppImage 或 `.deb`：由包管理器更新，应用内更新会被禁用。

### 9.5 构建时提示缺少 changelog

```text
CHANGELOG.md has no notes for 0.1.1: add a "## 0.1.1" section
```

在 `CHANGELOG.md` 添加完全匹配版本号的二级标题。

### 9.6 CI 上传失败

- 确认 `MYGO_UPDATER_PRIVATE_KEY` Secret 已设置；发布工作流会先检查它是否为空，为空会直接失败，避免发出一个没有更新清单的版本。
- 确认 Secret 的内容与 `mygo.json` 的公钥匹配。
- 确认 workflow 有 `contents: write` 权限。
- 确认标签版本与 `mygo.json` 一致；不一致会在第一步失败。

## 10. 版本策略

- 只支持向前更新，不支持降级。
- 建议按语义化版本递增：修复用 `0.1.1`，功能用 `0.2.0`。
- 每次发布必须有新的 `## <version>` 小节。
- 第一个带更新功能的版本发布后，之前的旧版本不会自动获得更新能力，需要用户手动安装一次。
- 如果私钥泄露，立即停止发布，生成新密钥对并发布一个使用新公钥的版本；旧用户需要手动安装这个过渡版本。
